# Diseño de Seguridad

El diseño de seguridad de **SIREDECI** se basa en una arquitectura por capas
que separa claramente el frontend (SPA Vue 3), el backend (API REST Django) y
la base de datos PostgreSQL. Sobre esta base se definen mecanismos de
autenticación, autorización y protección de datos.

---

## Arquitectura de Seguridad {#arquitectura-seguridad}

- **Capa de Presentación (Frontend):**
  - Aplicación Vue 3 desplegada en Vercel.
  - No almacena contraseñas ni secretos de servidor.
  - Mantiene solo información mínima de sesión en `localStorage` (tipo de
    usuario, identificador de ciudadano y/o token de sesión).

- **Capa de API (Backend Django + DRF):**
  - Expuesta como API REST en Render.
  - Endpoints públicos y privados diferenciados por URL y permisos.
  - Usa el modelo `Usuario` para usuarios internos y `Ciudadano` para
    ciudadanos.

- **Capa de Datos (PostgreSQL):**
  - Solo accesible por el backend, nunca directamente desde el frontend.
  - Tablas separadas para usuarios internos, ciudadanos, denuncias, reportes y
    auditoría.

- **Comunicación segura (prevista):**
  - Todo el tráfico entre frontend (Vercel) y backend (Render) se realiza
    mediante HTTPS.

---

## Flujo de Autenticación {#autenticacion}

Se contemplan dos tipos principales de autenticación:

1. **Ciudadanos:**
   - Acceden a través de `LoginCiudadano.vue`.
   - Credenciales: DNI + fecha de emisión del DNI.
   - El backend (vista `CiudadanoLoginView`) valida las credenciales y genera
     un `session_token` asociado al `Ciudadano`.
   - El frontend almacena `id_ciudadano` y el token de sesión en
     `localStorage` para identificar al ciudadano en operaciones posteriores
     (registro y consulta de denuncias).

2. **Usuarios internos (personal municipal / admin):**
   - Basados en el modelo `Usuario` con autenticación tipo Django.
   - Se prevé el uso de JWT (`rest_framework_simplejwt`) para exponer tokens a
     clientes internos si fuera necesario.

En ambos casos, las credenciales nunca se almacenan en el frontend y las
operaciones sensibles se realizan exclusivamente a través de la API.

---

## Sistema de Autorización RBAC {#rbac}

El control de acceso se diseña bajo un enfoque **RBAC (Role-Based Access
Control)**:

- **Roles lógicos:**
  - Ciudadano.
  - Operador municipal.
  - Jefe de área.
  - Administrador del sistema.

- **Backend:**
  - Uso de permisos de Django REST Framework:
    - Endpoints públicos: `AllowAny` (estadísticas públicas,
      `/api/public/reportes/...`).
    - Endpoints protegidos: `IsAuthenticated` + permisos personalizados
      (`IsStaffLike`, verificación de `PersonalMunicipal` activo, etc.).
  - Vistas de `apps.personal` validan que el usuario autenticado pertenezca al
    área responsable antes de permitir asignar o gestionar denuncias.

- **Frontend:**
  - Navegación separada por espacio:
    - Rutas `/ciudadano/...` para ciudadanos.
    - Rutas `/municipal/...` y `/admin/...` para usuarios internos.
  - Utilidades en `src/utils/roles.js` (o similar) para decidir la ruta
    inicial según el rol.

## Encriptación de Datos {#encriptacion}

- **En tránsito:**
  - El diseño asume despliegue en Render y Vercel sobre HTTPS, garantizando
    encriptación TLS entre cliente y servidor.

- **En reposo:**
  - Los passwords de usuarios internos se almacenan usando los mecanismos
    estándar de Django (`PBKDF2` u otro algoritmo configurado) sin guardar
    contraseñas en texto plano.
  - Los datos críticos (por ejemplo, DNI de ciudadanos) se almacenan en la
    base de datos con acceso limitado al backend.

---

## Gestión de Sesiones {#sesiones}

- **Ciudadanos:**
  - Sesión basada en el `session_token` retornado por la API de login.
  - Información mínima guardada en `localStorage` para identificar al
    ciudadano.
  - Los endpoints como `/api/denuncias/mis-denuncias/` filtran por
    `id_ciudadano` para evitar fuga de información entre usuarios.

- **Usuarios internos:**
  - Sesión administrada por el sistema de autenticación de Django.
  - Se contempla el uso de JWT para integrar otras aplicaciones o
    clientes internos (biblioteca `rest_framework_simplejwt` incluida).

El diseño considera la posibilidad de expirar tokens y cerrar sesión desde el
frontend, aunque las políticas de expiración avanzadas se dejan para fases
posteriores.

---

## Auditoría y Logs {#auditoria}

- Se define un módulo de reportes/auditoría (`apps.reportes`) que centraliza
  la generación de indicadores y permite, en fases posteriores, registrar
  eventos relevantes (cambios de estado de denuncias, accesos administrativos,
  etc.).

- Django registra por defecto errores de servidor y excepciones no
  controladas; el diseño contempla aprovechar estos logs para monitoreo y
  futuras integraciones con herramientas externas (por ejemplo, servicios de
  logging en la nube).

En versiones posteriores se podrían añadir:

- Tablas de auditoría específicas para operaciones críticas.
- Integración con sistemas SIEM para correlación de eventos de seguridad.
