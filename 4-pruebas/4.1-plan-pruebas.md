# Plan de Pruebas

Este documento describe la estrategia general de pruebas para SIREDECI, los tipos de pruebas considerados
y el alcance inicial que se implementará en esta fase.

## Estrategia de Pruebas

En esta etapa el enfoque principal será:

- **Priorizar el backend** (API Django REST), ya que concentra la lógica de negocio.
- **Empezar por pruebas unitarias y de integración ligera** sobre endpoints clave.
- **Estandarizar la forma de ejecutar las pruebas** para que cualquier desarrollador pueda correrlas fácilmente.

Línea de tiempo propuesta:

1. **Fase 1 – Backend (actual)**
   - Configuración de `pytest` y `pytest-django`.
   - Pruebas unitarias para módulos críticos del backend:
     - Notificaciones (internas y ciudadanos).
     - Denuncias (registro, consulta básica).
     - Estadísticas públicas y reportes.

2. **Fase 2 – Frontend (posterior)**
   - Configuración de framework de pruebas para Vue 3 (Vitest).
   - Pruebas unitarias de componentes críticos (formularios de denuncia, dashboards principales).

3. **Fase 3 – Pruebas funcionales (posterior)**
   - Casos de prueba por flujo completo (end-to-end manuales o automatizados).
   - Enfoque en flujos de usuario más importantes.

4. **Fase 4 – Pruebas de seguridad (posterior)**
   - Checklists y validaciones específicas sobre autenticación, autorización y protección básica OWASP.

La prioridad inmediata es **consolidar las pruebas unitarias de backend** (secciones 19.1 y 19.2).

## Tipos de Pruebas

Los tipos de pruebas considerados en el proyecto son:

- **Pruebas unitarias de backend**
  - Verifican la lógica de vistas (views), serializers, permisos y utilidades.
  - Se ejecutan con `pytest` y `pytest-django`.

- **Pruebas de integración ligera (backend)**
  - Usan `APIClient` para invocar endpoints REST.
  - Verifican que la vista, permisos y modelo trabajen juntos correctamente.

- **Pruebas unitarias de frontend (planificadas)**
  - Se realizarán más adelante con Vitest sobre componentes Vue 3.

- **Pruebas funcionales / end-to-end (planificadas)**
  - Casos de prueba por flujo (registro de denuncia, gestión municipal, consulta pública, etc.).
  - Inicialmente pueden documentarse como pruebas manuales.

- **Pruebas de seguridad (planificadas)**
  - Revisiones específicas de autenticación, autorización, manejo de sesiones, etc.

En esta fase se implementarán principalmente **pruebas unitarias e integración de backend**.

## Alcance de Pruebas

### Alcance inicial (implementado/por implementar ahora)

Módulos de backend priorizados:

- **Notificaciones**
  - Endpoints internos de notificaciones de usuario (`/api/notificaciones/usuario/...`).
  - Endpoints de notificaciones para ciudadanos (`/api/ciudadanos/notificaciones/...`).

- **Denuncias**
  - Registro de denuncia ciudadana.
  - Consulta de denuncias del ciudadano ("Mis denuncias").
  - Consulta básica para personal municipal.

- **Reportes y estadísticas públicas**
  - Endpoints públicos bajo `/api/public/reportes/...` (estadísticas de denuncias, tendencias geográficas, ranking de áreas).

Para cada módulo se buscará tener al menos:

- Casos "felices" (200 OK, datos correctos).
- Casos de error básicos (403/401 cuando aplique, 400 para datos inválidos, 404 cuando el recurso no exista).

### Alcance futuro (documentado pero no implementado todavía)

- **Pruebas unitarias de frontend**:
  - Componentes de formularios de denuncia.
  - Pantallas de dashboard (municipal, admin, ciudadano).

- **Pruebas funcionales**:
  - Flujos completos de registro, asignación y resolución de denuncias.

- **Pruebas de seguridad** (sección 21.x):
  - Revisión OWASP Top 10 adaptada a la arquitectura del sistema.

Este documento sirve como guía general; los detalles técnicos de implementación de pruebas unitarias se encuentran en `4.2-pruebas-unitarias.md`.\n
