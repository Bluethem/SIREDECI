# Implementación de Seguridad

En esta sección se describe cómo se implementaron los mecanismos de seguridad en
la aplicación **SIREDECI**, tanto en el backend (Django REST Framework) como en
el frontend (Vue 3). Se cubren las decisiones tomadas para autenticación,
autorización por roles, protección de datos y consideraciones mínimas de
endurecimiento.

---

## Autenticación

### a) Backend

El backend utiliza el sistema de autenticación de Django y APIs REST a través de
Django REST Framework.

- **Usuarios internos** (administradores y personal municipal):
  - Se basan en el modelo `Usuario` (`apps.usuarios.models.Usuario`).
  - Soportan login tipo Django (email/nombre de usuario + contraseña).
  - Se usan permisos personalizados como `IsStaffLike` para diferenciar
    usuarios con acceso a reportes internos y módulos de gestión.

- **Ciudadanos**:
  - Se autentican a través de la vista `CiudadanoLoginView` en
    `apps.ciudadanos.views`.
  - Credenciales: `dni` + `fecha_emision_dni`.
  - En caso de validación correcta se devuelve un `session_token` y los datos
    del ciudadano (`id_ciudadano`, nombre, etc.).
  - Este token se usa desde el frontend para mantener la sesión de ciudadano
    (almacenado en `localStorage`).

### b) Frontend

En el frontend se utilizan servicios dedicados para autenticación:

- `src/services/auth.js` maneja:
  - Login de ciudadano (`loginCiudadano`), consumiendo el endpoint de
    `CiudadanoLoginView`.
  - Login de usuarios internos (admin/municipal), consumiendo los endpoints del
    backend de Django.
  - Almacena en `localStorage`:
    - Datos del usuario/ciudadano (`user`).
    - Tipo de usuario (`tipo_usuario`: ciudadano, admin, municipal).
    - Token o `session_token` según corresponda.

Las vistas como `LoginCiudadano.vue` y `LoginAdmin.vue` consumen estos
servicios y, tras un login exitoso, redirigen a los dashboards correspondientes
mediante Vue Router.

## Autorización y Roles

### a) Backend (permisos)

La autorización se implementa usando permisos de Django REST Framework y
comprobaciones adicionales en las vistas.

- Endpoints internos de reportes (`/api/reportes/...`) y municipal
  (`/api/municipal/...`):
  - Requieren `IsAuthenticated` + permiso personalizado `IsStaffLike`.
  - En las vistas de `apps.personal` se verifica además que el `Usuario`
    autenticado tenga un `PersonalMunicipal` activo asociado.

- Endpoints públicos de reportes (`/api/public/reportes/...`):
  - Tienen permiso `AllowAny`, permitiendo acceso sin autenticación.

- Endpoints de denuncias (`/api/denuncias/...`):
  - Permiten registro de denuncias tanto anónimas como vinculadas a un
    `Ciudadano`.
  - El método `mis_denuncias` filtra por `id_ciudadano` para que cada
    ciudadano solo vea sus propias denuncias.

### b) Frontend (rutas y navegación)

En el frontend se utiliza Vue Router para separar los espacios según rol:

- Rutas de **ciudadano** (`/ciudadano/...`):
  - Accesibles tras un login de ciudadano.
  - El dashboard y vistas como `MisDenuncias` leen el usuario actual desde
    `authService`/`localStorage`.

- Rutas de **admin** (`/admin/...`) y **municipal** (`/municipal/...`):
  - Protegidas mediante guards que comprueban si hay un usuario interno válido
    en sesión y si tiene los roles apropiados.
  - Se aprovechan utilidades de `src/utils/roles.js` para mapear los permisos y
    decidir la ruta por defecto del usuario interno.

- Rutas **públicas** (`/public/...`):
  - No requieren autenticación.
  - Ejemplos: `EstadisticasPublicas.vue`, `ReportesPublicos.vue`, consulta
    pública de denuncias.

Se corrigieron bucles de redirección en el router ajustando la función que
calcula la ruta por defecto del admin cuando no hay roles válidos.

## Manejo de Sesiones y Datos Sensibles

- En el frontend:
  - La información mínima de sesión (usuario, tipo de usuario, tokens) se
    almacena en `localStorage` del navegador.
  - Los componentes leen estos datos a través de `authService` para determinar
    si hay sesión activa y qué opciones mostrar.

- En el backend:
  - Los modelos de usuario y ciudadano no exponen directamente campos
    sensibles en las respuestas de la API.
  - La lógica de creación de denuncias (`DenunciaCreateSerializer`) valida que
    la información obligatoria esté presente para evitar inconsistencias en la
    base de datos.

Se recomienda, para despliegues en producción, utilizar siempre HTTPS para
proteger las credenciales y tokens en tránsito.

---

## Validaciones y Manejo de Errores

- **Denuncias**:
  - Validación de campos obligatorios (título, descripción, categoría,
    ubicación) en el backend.
  - En el frontend, formularios como `RegistrarDenuncia.vue` y
    `LoginCiudadano.vue` incluyen validaciones básicas (formatos de DNI,
    fecha, campos requeridos) antes de enviar la solicitud.

- **Autenticación**:
  - Respuestas claras cuando el login falla (por ejemplo, mensaje de error en
    `LoginCiudadano.vue` si DNI/fecha no son correctos).
  - En caso de errores 401/403 en endpoints protegidos (personal municipal),
    se registran mensajes en el backend y se guía al usuario para volver a
    iniciar sesión.

- **Manejo de excepciones en reportes públicos**:
  - Endpoints de estadísticas públicas capturan errores y devuelven estructuras
    seguras por defecto (listas vacías, contadores en 0) para no exponer
    trazas internas al usuario final.

## Consideraciones de Endurecimiento (Hardening)

Aunque el alcance del proyecto se centra en la correcta funcionalidad y
pruebas básicas, se han considerado las siguientes buenas prácticas mínimas:

- Separación clara entre endpoints públicos (`/api/public/...`) y privados
  (`/api/reportes/...`, `/api/municipal/...`).
- Uso de permisos y verificaciones de rol para evitar que un ciudadano pueda
  acceder a vistas internas de gestión.
- Validación de datos de entrada en serializers y vistas, reduciendo el riesgo
  de errores de integridad.
- Centralización de la configuración de Axios en `src/services/api.js`, lo que
  facilita agregar cabeceras de seguridad adicionales (por ejemplo,
  `Authorization`) si se migra a JWT u otro esquema en producción.

En trabajos futuros se podría complementar esta sección con:

- Políticas de contraseñas más estrictas para usuarios internos.
- Rotación y expiración de tokens de sesión.
- Auditoría y logging avanzado de acciones sensibles (cambios de estado de
  denuncias, generación de reportes, etc.).
