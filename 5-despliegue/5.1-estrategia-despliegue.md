# Estrategia de Despliegue

Este documento describe la estrategia de despliegue del sistema **SIREDECI**,
considerando el backend (Django + PostgreSQL) y el frontend (Vue 3 + Vite).

---

## Metodología

El despliegue se basa en una arquitectura **frontend estático + API REST**:

- **Backend:**
  - Framework: Django 5 + Django REST Framework.
  - Base de datos: PostgreSQL.
  - Plataforma: Render (Web Service + PostgreSQL Managed DB).
  - Server de aplicación: `gunicorn` sirviendo `config.wsgi:application`.

- **Frontend:**
  - Framework: Vue 3 (Vite) con Vitest para pruebas unitarias.
  - Plataforma: Vercel (hosting de sitios estáticos / SPA).
  - Consumo de la API del backend mediante Axios.

Flujo general:

1. Desarrollador hace *push* al repositorio remoto.
2. Render (backend) y Vercel (frontend) detectan el cambio y ejecutan el build.
3. Si el build es exitoso, se publica la nueva versión.
4. En caso de fallo, se mantiene la versión anterior publicada.

## Configuración de Despliegue

### Backend (Render)

- **Root del servicio:** `siredeci-app/backend`.
- **Build Command:**

  ```bash
  pip install -r requirements.txt && \
  python manage.py migrate && \
  python manage.py collectstatic --noinput
  ```

- **Start Command:**

  ```bash
  gunicorn config.wsgi:application --bind 0.0.0.0:8000
  ```

- **Variables de entorno recomendadas:**

  - `DJANGO_SETTINGS_MODULE = config.settings.direct`
  - `DJANGO_SECRET_KEY = <clave aleatoria segura>`
  - `DJANGO_DEBUG = False`
  - `DJANGO_ALLOWED_HOSTS = siredeci.onrender.com`
  - `DATABASE_URL = postgres://user:pass@host:port/dbname` (proporcionada por Render)
  - `CORS_ALLOWED_ORIGINS = https://siredeci.vercel.app`

El archivo `config/settings/direct.py` está preparado para leer estas
variables y configurar `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, la base de datos
(vía `dj-database-url`) y CORS.

### Frontend (Vercel)

- **Root del proyecto:** `siredeci-app/frontend`.
- **Build Command:** `npm run build`.
- **Output Directory:** `dist`.

- **Variables de entorno:**

  - `VITE_API_BASE_URL = https://siredeci.onrender.com/api`

En el código, el cliente Axios central (`src/services/api.js`) usa esta
variable para construir la URL base de la API.

## Calendario

Se adopta un enfoque simple de despliegue **continuo**:

- Despliegues frecuentes a un entorno único (producción) a medida que se
  consolidan funcionalidades.
- Antes de un despliegue significativo se ejecutan pruebas unitarias de backend
  (`pytest`) y de frontend (`npm run test:unit`).

Hitos principales:

- **Iteración 1:** despliegue funcional inicial (login ciudadano, registro de
  denuncias, consultas públicas).
- **Iteración 2:** despliegue con módulo municipal y paneles administrativos.
- **Iteración 3:** endurecimiento de seguridad y pruebas adicionales.

---

## Roles y Responsabilidades

- **Desarrollador principal:**
  - Mantiene el repositorio y la configuración de Render/Vercel.
  - Ejecuta pruebas locales antes de hacer *push*.

- **Revisor (si aplica):**
  - Revisa cambios críticos de seguridad y de esquema de base de datos.

- **Operaciones (rol asumido por el desarrollador en este proyecto académico):**
  - Supervisa el estado de los servicios en Render/Vercel.
  - Gestiona secretos y variables de entorno.

## Plan de Rollback

Dado que Render y Vercel mantienen el historial de despliegues, el rollback se
basa en volver a una versión anterior estable.

### Backend (Render)

- Si un despliegue introduce un error crítico:
  - Se identifica el último despliegue estable desde el panel de Render.
  - Se selecciona la versión anterior y se activa desde la interfaz de Render
    (*rollback* manual).

### Frontend (Vercel)

- Vercel permite seleccionar un despliegue anterior y promoverlo como
  producción.
- Alternativamente, se puede desplegar una rama/tag anterior.

### Buenas prácticas adicionales

- Mantener cambios de base de datos (migraciones) pequeños y reversibles.
- Documentar en los commits cualquier migración destructiva.
- Evitar cambios masivos no probados en una sola iteración de despliegue.
